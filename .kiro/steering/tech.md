# 技術スタック

## アーキテクチャ

ESP32-CAM上で動く単一のArduinoファームウェア。起動時にカメラとWiFiを初期化し、以降は「撮影 → HTTPSでPOST → 次の周期まで待つ」を繰り返す単純なループで動く。サーバー側の処理(判定・保存・表示)は持たず、端末は撮影と送信だけを担う。撮影と送信は同じ周期で行い、画像だけを高頻度に送るような分離はしない。

無人で長時間動かす前提のため、どの段階で失敗しても次の周期へ進めることと、ハングしても再起動で復帰できることを、機能より優先する設計判断とする。

## コア技術

- **言語**: C++(Arduino)
- **フレームワーク**: Arduino core for ESP32(PlatformIOの`framework = arduino`)。カメラは`esp_camera`(esp32-camera)を使う
- **ビルド・書込み**: PlatformIO。`platform = espressif32`、`board = esp32cam`
- **対象ハードウェア**: AI Thinker ESP32-CAM互換ボード

## ハードウェアの実測値

手元の検証機で確認した値。設計や設定の既定値はこれを根拠にする。

- **SoC**: ESP32-D0WD-V3(rev3.1)、flash 4MB
- **PSRAM**: 約4MB。フレームバッファはPSRAMに置く(`CAMERA_FB_IN_PSRAM`)。ビルドフラグに`-DBOARD_HAS_PSRAM -mfix-esp32-psram-cache-issue`が要る
- **カメラ**: OV2640(PID `0x26`)。ピン配置はAI Thinker ESP32-CAMの標準配置(XCLK=GPIO0、SIOD=GPIO26、SIOC=GPIO27、PWDN=GPIO32、RESETなし)
- **画像**: UXGA(1600x1200)のJPEG、`jpeg_quality=10`で約221KB。起動直後の数フレームは露出やホワイトバランスが安定しないため捨ててから使う
- **書込み**: CH340のUSBシリアル経由で自動リセット書込みができ、GPIO0のジャンパー操作は要らない。シリアル速度は115200bps
- **向き**: 基板の取り付け向きによって画像が90°回転して写ることがある。補正は設置で合わせるか、センサーのflip/mirror設定で行う(OV2640のセンサー設定では90°回転はできず、上下・左右の反転だけが可能)

## 開発標準

### 設定と秘密値
送信先URL・デバイス用トークン・WiFiのSSIDとパスワード・撮影間隔・画像の反転の指定は、書込み時の設定として与える。どの駐車場の画像かは、駐車場ごとに発行したデバイス用トークンでCMSが判別するため、端末に別の識別子は持たせない。秘密値(トークン、WiFiパスワード)と現地固有の値(SSID、送信先URL)はリポジトリにコミットしない。コミットするのは値を伏せた雛形だけにし、実際の値はgitignore対象のファイルか書込み時の外部からの注入で与える。具体的な注入方法はspecのdesignで決める。シリアルログにも秘密値を出さない。

### 通信
送信はHTTPSに限る。サーバー証明書は検証する(検証を無効にした接続で本番へ送らない)。

### コード品質
コードコメントには、コードから読み取れない理由(ハードウェアの癖、ワークアラウンドの理由など)だけを書く。

### テスト
ハードウェアに依存しない判断(再試行の判定、設定値の検証など)は、ホスト上で動く`pio test -e native`の単体テストで確かめる。カメラ・WiFi・HTTPSの動作は実機で確かめる。

## 開発環境

### 必要なツール
- PlatformIO Core(`~/.platformio/penv/bin/pio`。PATHには入っていないためフルパスで呼ぶ)
- 検証時点の版: PlatformIO Core 6.2.0、`espressif32` 7.1.3、Arduino core for ESP32 2.0.17
- USBシリアルは`/dev/ttyUSB0`(CH340)

### よく使うコマンド
```bash
# ビルド
~/.platformio/penv/bin/pio run
# 書込み
~/.platformio/penv/bin/pio run -t upload
# シリアルモニタ
~/.platformio/penv/bin/pio device monitor
```

## 重要な技術的判断

- **判定はサーバー側に寄せる**: 端末で台数を数えたり混雑を判定したりしない。ESP32の計算資源では精度が出にくく、判定方法を変えるたびに現地の端末を書き換えることになるため
- **撮影と送信を同じ周期にする**: 5分間隔で混雑状況を更新するには最新の1枚があれば足りる。間隔を分けると状態管理が増える割に得るものがない
- **自己回復を優先する**: 設置場所は手が届きにくく、開催中に人が復旧作業をする前提を置かない。失敗は次周期の再試行で吸収し、固まった場合はウォッチドッグで再起動する
